# dev.to article

dev.to renders a subset of Markdown, strips table styles, cannot show SVG or relative image paths, and is read on
phones. The article lives twice: the repo copy (the source, in `docs/articles/`) and the dev.to copy (uploaded image
URLs, `{% details %}` spoilers). The rules below came from three published articles about two converters and their
comparison with Claude models.

## The rules

1. **The repo copy is the source.** The dev.to copy differs only in format (uploaded image URLs, spoilers). A later
   change goes to both on the same day, and the PR says which edits the user still has to make in the dev.to editor.
2. **Every number comes from a data file,** named in a comment at the top of the article. After any rescoring or new
   run, recompute the article's numbers; before publishing, one pass that checks each number, table and chart
   against its source.
3. **Nothing the reader cannot run.** Every command, flag and option in the article is in the version on npm when the
   article goes out. If the article needs a new flag, the release comes first. `scripts/article-check.js --package
   <name>` compares the article's flags with the published README.
4. **dev.to format.** PNG charts at 2× (no SVG), images uploaded or by absolute URL, at most 4 tags, a 1000×420 cover,
   tables that fit (short headers, `&nbsp;` between a number and its unit, no `<br>` in cells), and prose that does
   not fit a table cell written as a list. See [dev.to format](references/devto-format.md).
5. **Link back on the day of publishing.** The dev.to URL goes into the repository (articles index, README
   "Documentation", the other parts of a series) in a PR from fresh `main`, not as a commit on an already merged
   branch. See [after publishing](references/after-publishing.md).
6. **The user publishes, and owns the claims about themselves.** Claude drafts, checks and formats; the user edits and
   presses Publish. Anything about the author (role, experience, motivation) is asked, never invented. Writes to the
   dev.to API are asked for by the plugin's hook.

## Workflow

| # | Step | Output |
| --- | --- | --- |
| 0 | Plan | Audience, title options, the 3 TL;DR claims, the data files they come from, what must be released first |
| 1 | Draft | `docs/articles/NN-slug.md` from [templates/article.md](templates/article.md): front matter `published: false`, TL;DR, Contents, sections, Limits, Acknowledgements, author line |
| 2 | Charts | SVG sources generated by a script from the data, PNG at 2× with [templates/render.sh](templates/render.sh); see [charts and cover](references/charts-and-cover.md) |
| 3 | Cover | 1000×420 from [templates/cover.svg](templates/cover.svg): title, one real example, the headline numbers from the TL;DR |
| 4 | Check | `node scripts/article-check.js <article> --package <name>` (in this skill's folder): no FAIL; WARNs read one by one |
| 5 | Editorial pass | Short sentences, final results only, scoring explained plainly, heavy details in spoilers; see [style](references/style.md) |
| 6 | PR | Article, images and an articles index line; the PR lists the data sources |
| 7 | Release first (if rule 3 needs it) | The package version with every flag the article uses is on npm (publishing:npm-release) |
| 8 | Publish (user) | The user pastes the dev.to version, uploads the images and cover, publishes |
| 9 | Link back | PR from fresh `main`: the URL in the articles index, README and the other parts; repo copy synced with any edits made on dev.to |
| 10 | Social (user) | A LinkedIn or similar post links the article; Claude may draft it, the user posts |

## When you finish a step

Say what is left for the user (edits in the dev.to editor, the publish itself, the social post) and which PR carries
the link back.
